= Erstellung einer IAM-Rolle und eines AWS Secrets Manager Secrets
:hardbreaks:
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
Sie können Kubernetes-Pods für den Zugriff auf AWS-Ressourcen konfigurieren, indem Sie sich als AWS IAM-Rolle authentifizieren anstatt dafür explizite AWS-Anmeldedaten bereitstellen zu müssen.


NOTE: Zur Authentifizierung mit einer AWS IAM-Rolle benötigen Sie einen Kubernetes-Cluster, der mit Amazon EKS oder Red Hat OpenShift bereitgestellt wurde.



[[create-an-aws-secrets-manager-secret]]
== Erstellen Sie einen AWS Secrets Manager-Schlüssel

Trident benötigt Anmeldeinformationen, um Storage auf der FSx for ONTAP SVM zu managen. Die  `vsadmin`Anmeldeinformationen lassen sich in einem AWS Secrets Manager Secret speichern.

Dieses Beispiel erstellt einen AWS Secret Manager Secret, um Trident CSI-Anmeldedaten zu speichern:

[source, console]
----
aws secretsmanager create-secret --name trident-secret --description "Trident CSI credentials" \
  --secret-string "{\"username\":\"vsadmin\",\"password\":\"<svm_password>\"}"
----


[[create-an-iam-policy]]
== Eine IAM-Richtlinie erstellen

Für die korrekte Ausführung von Trident-Berechtigungen sind ebenfalls AWS-Berechtigungen erforderlich. Daher müssen Sie eine Richtlinie erstellen, die Trident die erforderlichen Berechtigungen erteilt.

Das folgende Beispiel erstellt eine IAM-Richtlinie mithilfe der AWS CLI:

[source, console]
----
aws iam create-policy --policy-name AmazonFSxNCSIDriverPolicy --policy-document file://policy.json \
  --description "This policy grants Trident CSI access to FSx for ONTAP and AWS Secrets Manager" \
  --query Policy.Arn --output text
----
Der Befehl gibt den Policy-ARN zurück. In den folgenden Befehlen kommt er zum Einsatz.

*JSON-Beispiel für Richtlinien*:

[source, json]
----
{
  "Statement": [
    {
      "Action": [
        "fsx:DescribeFileSystems",
        "fsx:DescribeVolumes",
        "fsx:CreateVolume",
        "fsx:RestoreVolumeFromSnapshot",
        "fsx:DescribeStorageVirtualMachines",
        "fsx:UntagResource",
        "fsx:UpdateVolume",
        "fsx:TagResource",
        "fsx:DeleteVolume"
      ],
      "Effect": "Allow",
      "Resource": "*"
    },
    {
      "Action": "secretsmanager:GetSecretValue",
      "Effect": "Allow",
      "Resource": "arn:aws:secretsmanager:<aws-region>:<aws-account-id>:secret:<aws-secret-manager-name>*"
    }
  ],
  "Version": "2012-10-17"
}
----


[[create-an-iam-role-for-pod-identity-or-an-iam-role-for-a-service-account-irsa]]
=== Erstellung einer IAM-Rolle für Pod Identity oder einer IAM-Rolle für ein Servicekonto (IRSA)

Sie können ein Kubernetes Servicekonto so konfigurieren, dass es mit EKS Pod Identity oder IAM roles for service accounts (IRSA) eine AWS Identity and Access Management (IAM) Rolle übernimmt. Pods, die für die Verwendung des Servicekontos konfiguriert sind, können dann auf AWS Services zugreifen, auf die die Rolle Zugriff haben darf.

[role="tabbed-block"]
====
.Pod Identity (EKS)
--
Amazon EKS Pod Identity-Zuordnungen bieten die Möglichkeit, Anmeldeinformationen für Ihre Anwendungen zu verwalten, ähnlich wie Amazon EC2-Instance-Profile Anmeldeinformationen für Amazon EC2-Instances bereitstellen.

*Installieren Sie Pod Identity auf Ihrem EKS-Cluster*:

Sie können die Pod-Identität über die AWS-Konsole oder mit dem folgenden AWS CLI-Befehl erstellen:

[listing]
----
aws eks create-addon --cluster-name <EKS_CLUSTER_NAME> --addon-name eks-pod-identity-agent
----
Weitere Informationen finden Sie in link:https://docs.aws.amazon.com/eks/latest/userguide/pod-id-agent-setup.html["Einrichten des Amazon EKS Pod Identity Agent"].

*Erstellen Sie trust-relationship.json*:

Erstellen Sie trust-relationship.json, damit der EKS-Dienstprinzipal diese Rolle für die Pod-Identität übernehmen kann. Erstellen Sie anschließend eine Rolle mit dieser Vertrauensrichtlinie:

[listing]
----
aws iam create-role \
  --role-name fsxn-csi-role --assume-role-policy-document file://trust-relationship.json \
  --description "fsxn csi pod identity role"
----
*trust-relationship.json-Datei*:

[source, json]
----

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "pods.eks.amazonaws.com"
      },
      "Action": [
        "sts:AssumeRole",
        "sts:TagSession"
      ]
    }
  ]
}
----
*Fügen Sie die Rollenrichtlinie der IAM-Rolle hinzu*:

Fügen Sie die Rollenrichtlinie aus dem vorherigen Schritt an die erstellte IAM-Rolle an:

[listing]
----
aws iam attach-role-policy \
  --policy-arn arn:aws:iam::aws:111122223333:policy/fsxn-csi-policy \
  --role-name fsxn-csi-role
----
*Erstellen Sie eine Pod-Identitätszuordnung*:

Erstellung einer Pod-Identitätszuordnung zwischen der IAM-Rolle und dem Trident Service-Konto (`trident-controller`).

[listing]
----
aws eks create-pod-identity-association \
  --cluster-name <EKS_CLUSTER_NAME> \
  --role-arn arn:aws:iam::111122223333:role/fsxn-csi-role \
  --namespace trident --service-account trident-controller
----
--
.IAM-Rolle für Servicekonten (IRSA) (nur EKS)
--
*Verwenden der AWS CLI*:

[listing]
----
aws iam create-role --role-name AmazonEKS_FSxN_CSI_DriverRole \
  --assume-role-policy-document file://trust-relationship.json
----
*Trust-Relationship.json-Datei:*

[source, json]
----
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::<account_id>:oidc-provider/<oidc_provider>"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "<oidc_provider>:aud": "sts.amazonaws.com",
          "<oidc_provider>:sub": "system:serviceaccount:trident:trident-controller"
        }
      }
    }
  ]
}
----
Aktualisieren Sie die folgenden Werte in der `trust-relationship.json` Datei:

* *<account_id>* - Ihre AWS-Konto-ID
* *<oidc_provider>* - Die OIDC-Provider-URL für Ihren EKS-Cluster. Sie erhalten sie durch Ausführen von:
+
[source, console]
----
aws eks describe-cluster --name my-cluster --query "cluster.identity.oidc.issuer" \
  --output text | sed -e "s/^https:\/\///"
----


*Zuordnung der IAM-Richtlinie zur IAM-Rolle*:

Nachdem die Rolle erstellt wurde, hängen Sie die Richtlinie (die im obigen Schritt erstellt wurde) mit diesem Befehl an die Rolle an:

[source, console]
----
aws iam attach-role-policy --role-name my-role --policy-arn <IAM policy ARN>
----
*Überprüfung der OIDC-Anbieterzuordnung*:

Die Zuordnung Ihres OIDC-Anbieters zu Ihrem Cluster lässt sich mit folgendem Befehl überprüfen:

[source, console]
----
aws iam list-open-id-connect-providers | grep $oidc_id | cut -d "/" -f4
----
Wenn die Ausgabe leer ist, weisen Sie IAM OIDC mit dem folgenden Befehl dem Cluster zu:

[source, console]
----
eksctl utils associate-iam-oidc-provider --cluster $cluster_name --approve
----
Wenn Sie  `eksctl`EKS verwenden, dient das folgende Beispiel zum Erstellen einer IAM-Rolle für ein Dienstkonto in EKS:

[source, console]
----
eksctl create iamserviceaccount --name trident-controller --namespace trident \
  --cluster <my-cluster> --role-name AmazonEKS_FSxN_CSI_DriverRole --role-only \
  --attach-policy-arn <IAM-Policy ARN> --approve
----
--
.IAM-Rolle für selbstverwaltetes OpenShift
--
Die selbstverwaltete OpenShift Deployment erstellt IAM-Rollen und ordnet sie den Clusterknoten zu. Die Trident IAM-Richtlinie wird der jedem Knoten zugewiesenen Rolle zugeordnet.

Zum Ermitteln der Instanz-IDs der Knoten in Ihrem Cluster wird der folgende Befehl ausgeführt:

[source, console]
----
oc get nodes -o jsonpath='{range .items[*]}{.spec.providerID}{"\n"}{end}'
----
Zum Ermitteln der jeder Instanz zugeordneten IAM-Rolle wird für jede Instanz der folgende Befehl ausgeführt:

[source, console]
----
aws ec2 describe-instances --instance-ids <instance-id> --query 'Reservations[*].Instances[*].IamInstanceProfile.Arn' --output text
----
Die IAM-Richtlinie wird jeder Rolle durch Ausführen des folgenden Befehls zugewiesen:

[source, console]
----
aws iam attach-role-policy --role-name <role-name> --policy-arn <IAM policy ARN>
----
